# 12 — Golden baselines (parent-owned, wave 0)

The baseline of record for every unit whose acceptance depends on legacy behaviour rather than on
row counts. Children read this file; children do not re-record baselines and do not edit this file.

## Baseline of record: `procs/oracle/transcripts/`

`procs/oracle/transcripts/` holds 24 immutable transcripts of the OW_BILLING PL/SQL entrypoints,
recorded by `procs/harness/oracle_record.py` from the declarative scenario set in `procs/scenarios/`
against the running Oracle estate:

| Module | Scenarios | Count | Oracle entrypoints exercised |
|---|---|---|---|
| `rating` | `RATING-001..008` | 8 | `pkg_rating.fn_usage_rating` |
| `invoicing` | `INVOICE-001..006` | 6 | `pkg_invoicing.*` |
| `plans` | `PLANS-001..005` | 5 | `pkg_plans.*` |
| `dunning` | `DUNNING-001..005` | 5 | `pkg_dunning.*` |

Each transcript carries its `module`, `scenario`, `inputs`, the declared `business_fields` (the
values recon compares), `probes`, the `oracle_entrypoint`, and `oracle_source_sha`.

## Provenance pin, verified

`procs/oracle/transcripts/ORACLE_SOURCE_SHA` is a SHA-256 over every `*.sql` under
`services/legacy-billing/db/oracle/` (relative path and bytes, in sorted order — see
`oracle_source_sha()` in `procs/harness/oracle_record.py`).

- Pinned: `0d326cad54d94cd64e8abb53585b37436eaad2193fdc15ba3596fbb8db3f0d55`
- Recomputed from the checked-out source on this branch: identical.
- All 24 transcripts carry that same `oracle_source_sha`, so the set is internally consistent and
  current with the source it claims to describe.

Verify before trusting a baseline in a recon report:

```sh
python3 - <<'PY'
import hashlib, pathlib
root = pathlib.Path("services/legacy-billing/db/oracle")
d = hashlib.sha256()
for p in sorted(root.rglob("*.sql")):
    d.update(str(p.relative_to(root)).encode()); d.update(b"\0")
    d.update(p.read_bytes()); d.update(b"\0")
print(d.hexdigest())
PY
cat procs/oracle/transcripts/ORACLE_SOURCE_SHA
```

A mismatch means the PL/SQL source moved after the transcripts were recorded: **stop and report it**.
Do not re-record to make it match — re-recording under a changed source silently redefines the
baseline the migration is being judged against. `oracle_record.py` refuses to overwrite without
`--allow-rerecord` plus a reason for exactly this purpose, and that call is the parent's.

## Cross-check against the Postgres transcript set

`procs/transcripts/` is the **Postgres** legacy-billing transcript set (entrypoints named
`billing.fn_*`, pinned by `SOURCE_SHA`/`FIXTURE_SHA`) from the earlier Postgres track. It is a
cross-check, not the baseline for this migration: the Oracle estate is the source being migrated,
so the Oracle-pinned set governs.

Measured on this branch: `business_fields` are **identical for all 24 of 24 scenarios** across the
two sets. So the two tracks agree on legacy behaviour today, and a future divergence between them
is a finding about the fixtures rather than about a unit's pipeline.

## What this pins, per unit

- `silver_rating` — `rating/RATING-001..008` (pilot; its recon is the first evidence the dictionary

Money comparison against a transcript is exact to the cent (T1), and the quarantine count is
reported next to it (T3), same as any other recon figure.

## Rules

1. A recon report that cites a transcript must cite the module, scenario id, and the
   `oracle_source_sha` it verified — not "matches the golden baseline".
2. Determinism for anything replayed alongside a transcript: `TZ=UTC`, `LC_ALL=C`, `LANG=C`, and
   the frozen clock via `scripts/tp-run-deterministic.sh`. Artifacts carry no embedded timestamps.
3. Transcripts are immutable. Re-recording is a parent action with a recorded reason; a child that
   believes a transcript is wrong stops and reports instead.
