## NOT DATA-PROVEN

`OW_BILLING.BILLING_AUDIT_LOG` holds **zero rows** today, in the fixture and in the live
source. This PASS therefore proves exactly two things:

1. Schema parity across all four columns through the mapping.
2. An empty-set assertion: source count 0 equals target count 0.

It proves **nothing about row content, timestamp precision or empty-string handling**,
because there were no rows to compare. Nobody may cite this run as data evidence. The unit
needs a fresh recon once `pkg_ow_util.log_msg` starts writing rows in the source.

## Conversion notes

- `logged_at` is `TIMESTAMP_NTZ`, not the `TIMESTAMP` the parent-owned mapping spec
  declares. The source column is an Oracle `DATE`: it keeps a time part and carries no
  zone, so a zoned Databricks `TIMESTAMP` would compare unequal to the same wall clock.
  UTC is assumed and declared (plan decision P1-D3). The mapping file is parent-owned and
  was not edited; the override lives in the loader and is raised as dialect feedback.
- `log_id` is `GENERATED BY DEFAULT AS IDENTITY`, which is what `seq_billing_audit_log`
  plus `trg_billing_audit_log_id` did: the sequence supplied a value only when the insert
  left `log_id` NULL. The identity is re-synced (`ALTER COLUMN log_id SYNC IDENTITY`)
  after every load that carries explicit keys, or the next generated value would collide.
- `module` and `message` apply the mapping's `empty_string_is_null` rule, matching Oracle,
  where an empty string is NULL.
- No foreign key was added: Oracle enforces none here, and the rows arrive from an
  autonomous transaction that can outlive a rolled-back caller.
