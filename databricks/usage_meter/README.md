# Per-tenant usage meter (`ow_tp`)

`USAGE_EVENTS` is a raw event table: nothing aggregated it per tenant, and rating read it
ad hoc at invoice time. This adds a meter that aggregates it on a cadence and hands the
current period to the billing application through Lakebase.

```
/Volumes/ow_tp/bronze/usage_meter_landing   JSON batches, one file per arrival
  -> ow_tp.bronze.usage_meter_events_raw    raw strings, COPY INTO, file-level idempotent
  -> ow_tp.silver.usage_meter_events        typed, validated, deduped on event_id
     ow_tp.silver.usage_meter_rejects       rows that cannot be attributed or metered
  -> ow_tp.gold.usage_meter_period          tenant x metric x calendar month
     ow_tp.gold.usage_meter_watermark       one row per stage
  -> Lakebase ow_tp / billing.usage_meter_current   current period only, one transaction
```

## Design points

- **Dedupe.** Silver is merged on `event_id`. A replayed event updates `seen_count` and
  `last_seen_at`; the first arrival's values win, so a replay with different units cannot
  move the meter. Two copies landing in the same `COPY INTO` share an `ingested_at`, so the
  surviving row is picked whole by `ROW_NUMBER` over a total order rather than column by
  column, and `seen_count` is counted over bronze rather than added to, so a retried stage
  converges instead of inflating. Rejects are merged, not inserted, for the same reason.
- **Late arrivals.** The watermark bounds *what is read*, never *what is recomputed*. An
  event's calendar month comes from `occurred_at`, so a backdated event reopens its own
  period: the meter recomputes exactly the tenant/metric/period cells the new rows touch,
  and leaves the rest of history alone. `is_late` and `late_event_count` record it.
- **Timestamps.** Oracle `DATE` carries a time part and Oracle `TIMESTAMP` is zoneless, so
  everything is `TIMESTAMP_NTZ` in Delta and `timestamp` in Postgres. No `timestamptz`,
  no wall-clock shift.
- **Period rule.** Rating includes an event when `TO_CHAR(occurred_at,'YYYYMMDD')` falls
  between the period bounds inclusive. The meter and the recon aggregate both use the
  event's own calendar date, so they agree with rating rather than with UTC midnight.
- **Rejects, not fail-open.** Missing tenant, non-positive units and unknown usage kinds
  go to the reject table with a reason and never reach the meter.
- **Lakebase.** The publish is one transaction: stage, delete every target row not in the
  stage (so a period that is no longer current leaves with it), upsert, stamp `billing.usage_meter_sync_state`. Readers see the old period or the new
  one, never a half-written one. Branch `mig-p1-w0` only; the code refuses any branch
  outside the allowlist and never touches `production`.

## Running it

```
python3 pipeline.py ingest | normalise | meter     # one stage per Lakeflow task
python3 lakebase_sync.py --branch mig-p1-w0        # publish current period
python3 recon_usage_meter.py                       # correctness report + idempotency rerun
python3 test_usage_meter.py                        # duplicate / late / empty / reject tests
python3 deploy_usage_meter_job.py [--run]          # create the PAUSED Lakeflow Job
python3 landing.py                                 # re-export the Delta snapshot to landing
```

Credentials come from `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID` and
`DATABRICKS_CLIENT_SECRET`; Lakebase credentials are minted per run by
`../migration/lakebase/with_lakebase_dsn.py`. Nothing here holds a credential value.

`deploy_usage_meter_job.py` uploads these files to the workspace and creates
`ow_tp_usage_meter`: `land_usage_events -> normalise_usage_events -> meter_usage ->
publish_to_lakebase`, two retries each, serverless, schedule **PAUSED**.
