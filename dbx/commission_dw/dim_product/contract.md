## Load semantics
1. `ddl.sql`: `DROP TABLE IF EXISTS` then `CREATE TABLE` (idempotent; the table is the unit's own).
2. `load.sql` step 1: initialise from the baseline snapshot with explicit keys.
3. `load.sql` step 2: NOT NULL guard on the feed (`assert_true`), because Spark inserts NULL where Oracle raised.
4. `load.sql` step 3: MERGE identical to the legacy statement — same ON key, same UPDATE list
   (`product_name`, `line_of_business` only; `product_key` is never rewritten), same INSERT list.
5. `run.py` executes 1–4 in order after asserting the feed row count equals the manifest-declared
   source volume; the first failing statement aborts the run (no error swallowing).

## Ambiguity classes (resolved up front)
- **Encoding / byte transparency**: inputs are UTF-8 CSV with a header row and explicit schema; strings
  are compared byte-for-byte, no trim, no case folding.
- **Malformed records**: `read_files(..., mode => 'FAILFAST')` — any extra/missing field or type
  violation fails the run; nothing is quarantined or skipped. NULL in a NOT NULL feed column fails
  the guard (legacy would raise `ORA-01400`). An empty CSV field is NULL.
- **Empty input**: an empty feed leaves the baseline rows unchanged (MERGE with no source rows);
  an empty baseline is not a valid run and the declared-volume assertion in `run.py` (manifest rows)
  rejects a feed whose row count differs from the extract.
- **Batch granularity**: full snapshot per run (the legacy procedure re-reads all of `PRODUCTS`
  each invocation; no period parameter applies to this dimension). Rerun for the same snapshot
  yields an identical row set excluding `loaded_at`.
